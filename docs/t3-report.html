T3 Connection: what the city can use from T3 Code Nullovation City Hall, task "T3 Connection: Research" · 17 November 2026 · T3 Code (Beta) v0.1.3 on Abdurrahman's PC

Everything in T3 that can be reached from the command line, and from a web page like the city, for two jobs: watching what goes on in T3 from the city, and sending prompts back. Scope as picked in T3 Connection Research, Round 1: the t3 command plus T3's other ways in (its server, its agent tools, its trace), not its database; read-only tests plus one short test thread; the installed version, with what newer releases add.

In short

The t3 command sees every agent's threads

t3 thread list --json and t3 thread show --json give each thread's status, agent, model, branch, pull requests, how many answers it waits for, and its latest messages, for any agent, with no sign-in on this PC.

Sending a prompt back works today

t3 thread send was tested: an idle thread takes it at once ("Sent."), a busy one queues it as its next turn ("Queued.") and nothing is interrupted. The city's T3 helper could run it the way it runs t3 thread start.

The command is thin; the agent tools are richer

The command is a wrapper over T3's agent tools at /mcp. Those can also steer a running turn, restart it, stop it, and answer an agent's question. Approvals can be answered only in T3's window.

Waiting on you is a count, not a status

While the test thread's question was open, its status stayed running; pendingRequestCount went to 1. A watcher has to read the count.

The command misses background work

With a command still running in the background (and the agent asking T3 to wait on it), thread show said completed for 54 seconds. T3's own window knows (pendingBackgroundTasks), but only over its private protocol.

A web page cannot use the agent tools

T3's HTTP routes answer any web page (Access-Control-Allow-Origin: *), but /mcp refuses any request that carries an Origin header, which every browser sends. The city page needs the helper, a watcher, or T3's own WebSocket.

New fact for the build round

You decided every agent's threads come to the city only in production, once it is no longer a web app. Three of the routes below would show every agent's threads while the city is still a web app.

T3 is six releases behind

v0.1.4 to v0.1.9 came out between 29 October and 11 November, and 0.1.10 nightlies on 16 November. v0.1.7 changed how questions show ("questions always move a thread out of Working").

The t3 command, all of it

%USERPROFILE%\.t3\bin\t3.cmd runs the CLI bundled in the app (T3 Code (Beta).exe as Node). Every thread command reads server-runtime.json for the server's address, gives itself a short full-access session straight from T3's data folder, calls the agent tools at /mcp, and revokes the session at the end. That is why it needs no sign-in on this PC, and why it needs T3 running.

Thread statuses, from T3's code: idle, preparing, queued, starting, running, waiting, completed, interrupted, failed, cancelled, rolled_back. A thread's status is its active run's, else its latest run's, else idle.

Watching T3

Whether a thread is working, waiting for you, or done

  • From the command or the tools: status on every thread, for every agent. t3_thread_list filters by status, so "everything running" is one call per project. There is no call for every project at once in the command; the tools page through projects with t3_project_list.
  • From T3's window protocol: the same status, pushed as it changes, plus the open request, the latest visible message, background tasks and the last error on each thread.
  • From Claude's hooks (today): working, waiting, done, failed and, since 0.1.88, background, for Claude only. Other agents run no Claude hooks.

A thread's latest messages

t3 thread show <id> --messages 3 --json gives the last three user and assistant messages whole. t3_thread_read with view: "activity" gives every timeline item: thinking, commands with their output, tool calls, questions, checkpoints, each with its run, status and time, paged and cut to a size asked for. Thread links come as t3-thread://v1/<id>.

Questions and approvals waiting on you

  • Tested: while the agent's question (Claude's AskUserQuestion) was open, thread show said running with pendingRequestCount: 1. The status waiting never showed. So the count is the signal, and the command does not say whether it is a question or an approval.
  • The kinds, in T3's code: command, file-read, file-change, mcp-elicitation and permission (approvals), user_input (questions), dynamic_tool_call, auth_refresh. T3's window protocol names the open one's kind and whether it blocks the run.
  • Newer T3: v0.1.7 says "fix(clients): questions always move a thread out of Working". Worth testing again after an update.
  • With --wait, start and send exit 2 when the agent waits for an answer.

Long commands still running in the background

  • Tested: a run ends when the agent's reply ends, even with a command still running in the background and the agent having called t3_background_wait on it. For 54 seconds thread show said completed while sleep 60 ran.
  • T3 does know. After the run settles, T3 works out each thread's pendingBackgroundTasks (commands, monitors, subagents, pull request watches; awaited or not) and sends it to its window. It is not in the command's or the tools' answers.
  • T3 wakes the thread when the command ends: a new run started by itself (runs 4 and 5 in the test), so the reply that follows is a real finish.
  • For the open task "Tasks says finished while it is still running long commands": the city's 0.1.88 hook reads Claude's transcript for commands still out, which covers Claude in T3 and in the terminal alike. T3's own pendingBackgroundTasks would be a second source, for every agent, but only over the window protocol.

How this was found

  • The command's own help, every command and subcommand, on this PC.
  • T3's server code, read in the app's bundle (resources\server.asar, apps/server/dist): the routes, the agent tools and their descriptions, the statuses, the origin rule, the WebSocket's checks, the background work. Read only; nothing in T3 was changed.
  • Read-only requests to 127.0.0.1:3773, t3 thread list and show, t3 service status, t3 trace summary, t3 connect status.
  • One test thread on Claude Haiku 5.5, in a scratch project made for it; the project and its thread were deleted afterwards (t3_project_delete), and the scratch folder removed.
  • T3's docs and releases: docs, outside agents, remote access, environment auth, overview, releases. The Mintlify mirror of the docs is gone (410).
  • Not tried: the city page opening T3's WebSocket; answering a question from outside; a T3 window inside a frame; anything on v0.1.4 or later.
